## Покрытые сценарии

- Вложенные окна, блокировка кнопок на корневом Canvas первым модальным окном, восстановление выбранного элемента и запасной выбор при его отключении; модальный экран принимает клики снаружи, верхнее окно принимает клики внутри.
- Удерживаемый Enter, открывающий клик мыши, одиночный Back/Cancel, навигация геймпадом и запрет перехода к элементу за границами активного окна.
- Повторные Open/Close, закрытие нижнего окна и родителя, уничтожение, выключение только UIWindow-компонента, выключение менеджера, выгрузка сцены, отмена затухания повторным Open.
- Отдельные leases, освобождение вне очереди, восстановление только прежде включённых actions, ожидание отпускания, сохранение чужих запросов, сообщения о незавершённой настройке.
- Исключения C#-подписчиков и повторный вход, включая закрытие/открытие окна из ContextChanged прямо во время AcquireContext, и отмена закрытия родителя повторным Open из Closed дочернего окна.
- Confirmed/Cancelled, отмена диалога при уничтожении родителя; центр круга, недоступный сектор и однократное подтверждение.
- Реальный EasyInput: вложенные контексты, **Look запрещён / Move разрешён**, отдельные BlockedActions, пользовательские карты **Player + UI**, Hidden/Inherit, выключение владельца, внешнее Disable/Enable UI-модуля и сохранение ограничений при rebinding.
- Cancel сначала отменяет rebinding; следующая отдельная команда закрывает окно. Gamepad East не становится новой привязкой. Независимый маршрут Cancel действует даже при выключенном UI-модуле. Отменяющее событие не попадает в Gameplay, возобновившийся после rebinding у UI-only окна.
- Полное окно управления: runtime capture/restore, отображение изменённой привязки, геометрия строк и ручек слайдеров. Значки берутся из `PlayerInputSettings.GetPresentation`.
- Переназначение Interact с E на K внутри EasyUI: существующий EasyInteraction-контроллер использует новую кнопку, затем замена контроллера сохраняет её. Старое E больше не выполняет действие.
- Стандартный LocalizedString и публичный EasyLocalization API: английский → русский → выключение представления → английский → повторное включение, с корректной отпиской.
- Локальная мастерская: действие на объекте открывает окно; круг выбирает BuildingDefinition через BuildingSession; выбор не списывает стоимость; подтверждение строительства списывает ресурсы; события обновляют остаток. Дочернее окно сохраняет блокировку родителя; чужой владелец BuildingPlacer остаётся после закрытия UI.

Тестовый ввод использует виртуальные устройства. Тесты временно включают IgnoreFocus и AllDeviceInputAlwaysGoesToGameView, затем восстанавливают настройки и удаляют свои устройства. Для Player-стенда также явно включён фоновый ввод; настройка восстанавливается перед завершением.

## Первый запуск в чистом проекте

Установлен именно **LocalTarball**, а не ссылка на embedded-папку общего проекта. Из установленного пакета импортирован Getting Started. В отдельной сборке последовательно выполнены: I → Enter → Enter → Esc → Esc → Esc → удержание R → верхнее направление стика → отпускание R. Проверены HUD, три независимых запроса, Cancelled, возврат выделения, возврат игрового управления и подтверждение круга. Клавиатурная цепочка не заменялась прямыми вызовами Open в этом прогоне.

В основном редакторе дополнительные сцены расположены под `Assets/PackageTests/EasyUI`: `GettingStarted/GettingStarted.unity`, `Cooperation/Workshop.unity`, `Controls/Controls.unity`. В мастерской E / gamepad West взаимодействует с терминалом, F2 добавляет древесину. После закрытия мастерской мышь выбирает место, ЛКМ строит, R/Q вращают, Esc отменяет. Камера неподвижна; FPS-контроллер для этого примера не создавался.

## Производительность

Development Player, Windows x64, **Core i7-14700KF**, 1280×720, VSync выключен, целевая частота 120. Графический запуск (`batchMode: false`), без Editor в измеряемом процессе. Ниже один воспроизводимый прогон; это не p95 и не гарантия для другого оборудования.

| Сценарий | Общее время | Среднее на операцию |
|---|---:|---:|
| 500 Open/Close уже созданного модального окна | 115,54 мс | **0,231 мс** |
| 200 созданий/уничтожений префаба из примера | 124,54 мс | **0,623 мс** |
| 200 шагов навигации геймпадом | 7,68 мс | **0,038 мс** |
| 200 переключений клавиатура/геймпад | 6,05 мс | **0,030 мс** |

Навигация и переключение устройств включают инъекцию событий и `InputSystem.Update`, поэтому не являются временем только EasyUI. В состоянии покоя с 1000 ранее открывавшимися неактивными окнами маркер EasyUI.Navigation составил в среднем **0,35 мкс/кадр**; с видимым меню — **2,73 мкс/кадр**. Средний Canvas.BuildBatch: **0** для скрытых окон, **0,36 мкс/кадр** с видимым меню за 120 кадров, включая начальные изменения выделения.

GC измерен через `GC Allocated In Frame` и [ProfilerRecorder](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Unity.Profiling.ProfilerRecorder.html). Калибровка показала, что `GC.GetAllocatedBytesForCurrentThread` в этой конфигурации Mono возвращает недостоверный ноль; соответствующее поле отчёта помечено **-1**, а не объявлено отсутствием аллокаций.

Базовый стенд с выключенным менеджером: **1141 Б/кадр**; 1000 скрытых окон: **1137 Б/кадр**; видимое меню плюс 1000 скрытых: **1182 Б/кадр**. Это общие аллокации процесса, а не исключительно EasyUI. Существенного роста idle GC от скрытых окон не обнаружено. Кадр с 500 Open/Close выделил около **4,90 МБ**, кадр с 200 созданиями префаба — **20,07 МБ**, включая Unity и стенд. Эти операции не являются zero-allocation.

После уничтожения тестовых окон: `remainingWindows = 0`, `liveSceneWindows = 0`; используемая managed-память около **5,55 МБ**, общая выделенная память Unity около **61,62 МБ**. Кэши Unity, шрифты и Input System остаются в процессе, поэтому память не должна возвращаться к нулю. Проверки leases и подписок дополняют эти замеры.

Решение для v0.1: не добавлять Jobs/Burst или сложный пул. uGUI работает на главном потоке, idle-нагрузка мала; для часто открываемого окна уже доступно повторное использование объекта сцены. Создание большого числа префабов следует распределять по кадрам. Раздельные Canvas окон ограничивают область перестроения; данные обновляются по событиям. Дальнейший пул имеет смысл после замера конкретного интерфейса игры.

Стенд воспроизводится из `Tools~/Verification`: импортируйте Getting Started, скопируйте Verification в Assets, создайте сцену через `EasyUI.Verification.Editor.VerificationBuilder.Create(folder, inventoryDefinitionPath)`, соберите её как Development Player и запустите с `-easyUIReport <absolute.json>`. Для первого запуска добавьте GettingStarted первым в сборку и передайте `-easyUISmoke <absolute.json>`. Тестовый offscreen-захват предназначен для Built-in renderer; обычные снимки выше получены из Game View общего проекта.

## Межпакетные изменения и границы

Исходники EasyInput, EasyLocalization, EasyBuilding, EasyResources и EasyInteraction в этой работе не изменялись. Адаптеры находятся в EasyUI `Samples~`, совместные игровые проверки — в локальных Assets. Использованы текущие локальные публичные API, в том числе подготовленные параллельно незакоммиченные изменения. В общий manifest добавлен EasyUI в `testables` с сохранением остальных записей.

EasyInput и EasyLocalization проверены совместно, временная подмена провайдера реальным адаптером завершена. Локализованная подсказка кнопки остаётся в адаптере EasyInput. EasyUI не копирует её реализацию и не владеет сохранением пользовательских настроек.

EasyFeedbacks-адаптер компилируется и соединяет Open/Select/Confirm с FeedbackService. Проигрывание конкретных пользовательских аудио/VFX/вибрационных пресетов и физический геймпад в этом прогоне не проверялись; нужны пресеты проекта и соответствующее оборудование. Прямой сценарий EasyMovement/ECM2 и EasyCombat не создавался: мастерская использует фиксированную камеру, а ввод таких контроллеров подключается адаптерами EasyInput.

Подтверждённый сценарий первой версии: Screen Space Overlay, Button, Slider, ScrollRect, окна/диалоги/круг. World-space/VR, UI Toolkit, split-screen, нативные всплывающие Dropdown и TMP InputField отдельно не проверялись. Вложенные Canvas пользовательского окна следует оставлять без Override Sorting: сортировкой управляет менеджер. Встроенные анимации — fade; сохранение стека и пул префабов не реализованы. Политики существующего окна не изменяются вслед за редактированием SO — они фиксируются на Open.

Работа оставлена в локальном репозитории EasyUI. Публикация в origin не выполнялась. Временный проверочный проект и сборки сохранены вне Unity Temp, в `EasyUIVerification~`, чтобы перезапуск редактора не удалял результаты.
